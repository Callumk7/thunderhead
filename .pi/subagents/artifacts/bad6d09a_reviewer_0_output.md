## Review

- **Correct:** GitHub access is bound to the configured team repository: `src/shared/repository-config.ts:38-42`, and every Contents API call supplies the bound owner/repository and resolved default branch. Path traversal, absolute paths, backslashes, common secret filenames, binary/NUL data, result counts, and file sizes are constrained in `src/tools/repository-read.ts:24-45, 87-145`.
- **Correct:** Search results return paths and URLs rather than GitHub snippets, and the query is repository-qualified in `src/tools/repository-read.ts:54-75`. I found no confirmed repository-scope escape, although parser-edge-case fuzzing remains advisable.
- **Correct:** Linear tools bind writes to the webhook issue ID, validate selected labels against existing team labels, and only add labels: `src/tools/linear-issue.ts:27-31, 121-138`; `src/shared/linear-client.ts:94-104`.
- **Correct:** Normal webhook-loop prevention is sound: only create-with-trigger or a genuine trigger-label transition dispatches, and delivery UUIDs are used for idempotency: `src/shared/linear-trigger.ts:19-27`; `src/channels/linear.ts:22-44`.
- **Correct:** Secrets remain host-side rather than tool parameters, `.env` is gitignored, and observability does not deliberately log prompts, tool arguments, or results.

- **Blocker — High:** **Conflict detection has a substantial TOCTOU window and can overwrite human edits or cross a team move.** The issue snapshot is checked at `src/tools/linear-issue.ts:67-123`, but label retrieval and the backup-comment operation occur before the unconditional update at `src/tools/linear-issue.ts:125-139`. The gateway mutation has no expected-version condition (`src/shared/linear-client.ts:73-75`). A human edit after the initial fetch—especially during the multiple comment API calls—will not be detected, will not be present in the backup, and can be overwritten. A team move after line 75 can similarly result in a write against the newly moved issue. Re-fetch immediately after backup and immediately before mutation; use a conditional mutation if Linear supports one, otherwise document and minimize the unavoidable final race.

- **Blocker — High:** **Repository secret exclusion is filename-denylist-only and raw content is sent to the model without redaction.** `read_repository_file` accepts any directly guessed path passing `isAllowedPath` and returns the entire decoded content (`src/tools/repository-read.ts:87-111`). The denylist at `src/tools/repository-read.ts:130-145` does not cover common credential-bearing paths such as `id_rsa`, `.docker/config.json`, `service-account.json`, `kubeconfig`, token-named files, or secrets embedded in ordinary source/configuration files. The claimed “only files found through listing/search” rule is also merely a tool description, not enforced statefully. Consequently, committed credentials can be disclosed to OpenRouter/Gemini and potentially copied into Linear. Add content-level secret detection/redaction, expand protected paths, and enforce discovery-before-read.

- **Blocker — High:** **Untrusted issue and repository content directly controls a model holding a Linear write capability, while critical policy is prompt-only.** The webhook title is inserted directly into the agent message (`src/channels/linear.ts:38`), full issue content and label names are returned at `src/tools/linear-issue.ts:38-44`, and raw repository content is returned at `src/tools/repository-read.ts:107-111`. The publish schema only checks lengths (`src/tools/linear-issue.ts:53-60`); it does not verify that repository tools were used, required sections exist, content does not contain secrets, or labels are from a security-reviewed allowlist. The only prohibitions are natural-language instructions at `src/agents/issue-strengthener.ts:87-98`. Prompt injection can therefore cause arbitrary replacement of the bound issue, disclosure of repository content, or addition of any existing team label. The blast radius is usefully limited to one issue and one mapped repository, but deterministic preconditions, structural validation, secret scanning, and preferably an explicit label allowlist are needed.

- **Note — Medium:** **Trigger-label removal does not cancel a run and can cause an agent-authored retrigger.** After a conflict, all current team labels are returned and any existing label ID may be added (`src/tools/linear-issue.ts:90-123`). If a human removes `ai:strengthen` during analysis, regeneration may select and re-add it at lines 121-138. The webhook then sees the trigger absent from prior label IDs and dispatches another run (`src/shared/linear-trigger.ts:19-27`). Require the trigger to remain attached before publication and prevent the agent from adding the trigger label itself.

- **Note — Low:** **Some operations are issue-bound but not team-bound.** `get_linear_issue` fetches labels from whatever team currently owns the issue without checking `ref.teamId` (`src/tools/linear-issue.ts:37-44`). `report_repository_unavailable` writes a comment without any team revalidation (`src/tools/linear-issue.ts:153-170`), and the moved-team path intentionally comments after detecting the mismatch (`src/tools/linear-issue.ts:75-87`). These comments are generic and do not disclose repository content, but they violate a strict immutable-team write boundary.

- **Note:** Tests do not cover the race, team-move behavior, trigger removal/re-addition, prompt-injection preconditions, content redaction, or allowed-label policy. In fact, the publish fixture contains only a Summary section (`src/tools/linear-issue.test.ts:33-39`), demonstrating that required output structure is not enforced.
